## 2. 机制：时间闸门（time-gate）+ cap-link

第三阶段上限 = `tower(min(基准×cap_mult, 宇宙上限), cap 塔层)`（`cap_tetrate`）。

**为什么不能靠资源比率 pacing**：塔高 ≥2 时 `上限 / 常数 ≡ 上限`（MegotaNum 塔表示丢失分数）——
`e1e2020550 / 120 ≡ e1e2020550`、`× 0.5` 同样。因此 `成本 = 0.5×上限` 与
`产出下限 = 上限/常数` 都会被塔顶吃掉，填塔时间退化为 ~1 游戏秒，与 divisor 无关。

**改为时间累积**：每买一层 `cap_tetrate` 前，循环需充能 `phase3.cycleSeconds` **物理秒**
（`js/sim/cycle.js`，engine 每 tick 用 `dtReal` 推进，买塔时归零）。产出侧保留 cap-link
（上限资源产出 ≥ 上限 / divisor）保证资源不是瓶颈。

- 循环是唯一闸门 → 每层恒定 ≈ `cycleSeconds` 物理秒，与塔高 / 速率 / 数值精度无关。
- cap-link 仅在**已叠至少一层 cap 塔**后生效，只作用于 `mass_energy`。
- 第三阶段成本用 `costFraction`（`cost = 当前上限 × fraction`），仅作形式约束。

## 3. 结果（`--phase3`）

起始：宇宙 9，上限 `1.000e2,020,580`。技术树 12 项（4 层塔 + 4 加速 + 3 晶体 + 1 引擎），
`cycleSeconds = 120`。

| 里程碑 | 物理时间 |
|---|---|
| 庞加莱折叠 I | 2.0min |
| 庞加莱折叠 II | 4.0min |
| 庞加莱折叠 III | 6.1min |
| 庞加莱折叠 IV | 8.1min |
| 全程（含加速/晶体/引擎） | 8.1min |

> 每层恰好 ≈ `cycleSeconds`（2 分钟），与塔高无关——时间闸门达成预期。

## 4. 结论

- **物理时间 pacing 达成**：每层塔恒定 `cycleSeconds` 物理秒。`divisor`（cap-link）退居次要，只保证资源充足。
- 调 `phase3.cycleSeconds` 即可整体调节第三阶段长度（如 180 → 每层 3 分钟）。
- 锚点 **eee120** 由 `p3_rate_4`（时间速率 ×eee120）在游戏内时间上兑现。
