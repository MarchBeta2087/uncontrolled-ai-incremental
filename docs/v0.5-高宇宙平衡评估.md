# v0.5 高宇宙平衡评估（第 7–9 宇宙停滞）

| 项目 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 撰写日期 | 2026-10-12 |
| 对应 | v0.5 多宇宙；`tools/balance-sim.mjs`；`config/universes.json` 的 `difficultyExponent` |
| 性质 | 估算性质（无头贪心模拟） |

## 1. 现象与复现

```bash
MAX_UNIVERSES=9 node tools/balance-sim.mjs --multiverse
```

旧配置（`difficultyExponent = 0.95`）下，模拟在第 7 宇宙停滞：

```
停滞（宇宙 7）：下一购买 gen:investment 需 1.11e+15 游戏秒
  gen investment: count=4.556e6 cost=7.344e224,261 have=9.750e224,258 prod=6.589e224,246/游戏秒
  ...
  globalMult=1.446e224,240 capMult=1.000e224,224 cap=1.000e224,324
```

即玩家资金 `9.75e224258`、下一生成器成本 `7.34e224261`、产出 `6.59e224246/游戏秒`，
需 `1.1e15` 游戏秒才能买下一个——实际卡死。第 8 宇宙同理。

## 2. 根因

`singularity.applyCrossUniverse` 的自适应难度：

```
universe:prod = capMult / (difficulty × metaProd^difficultyExponent)
```

其中 `metaProd` 为全部元进度产出乘子（成就 / 晶体升级 / 跨宇宙升级）。于是

```
产出 / 上限  ≈  count × baseProd / (baseCap × metaProd^difficultyExponent)
```

- 该比值**与宇宙无关**，随 `metaProd` 增长而**下降**（阻尼项在分母）。
- 生成器成本按 `growth^count` 几何增长，而产出对 `count` 线性；`count` 受 `log(上限)` 约束，
  因此元进度一旦变强，产出就被阻尼压到生成器成本之下，形成"高宇宙卡死"。
- 与 `difficulty` 无关（各宇宙均为 `1`）。

## 3. 修复：降低 `difficultyExponent`

`config/universes.json`：`difficultyExponent` **0.95 → 0.5**。

实测（`MAX_UNIVERSES=9 --multiverse`）：宇宙 1–9 **全部可达，无停滞**。

| 宇宙 | 用时（旧 0.95） | 用时（新 0.5） |
|---|---|---|
| 1 | 1.60h | 1.60h |
| 2–6 | 瞬发（≤3s） | 0.0s |
| 7 | **停滞** | 0.0s |
| 8 | — | 0.7s |
| 9 | — | 0.2s |

## 4. 遗留：高宇宙仍近乎瞬发

宇宙 2–8 用时 < 1s——元进度（成就 / 晶体 / 跨宇宙升级）相对单宇宙上限仍过强。
这只是把"卡死"变成"瞬发"，**未达成 v0.5 设计的「越玩越强但每宇宙数分钟」**。

结构性重平衡的候选（另立 PR）：
1. **每宇宙 `difficulty` 曲线**：让 `difficulty` 随宇宙编号上升，抵消元进度；
2. **生成器成本随上限缩放**：使 `count` 与上限同步，避免几何成本提前触顶；
3. **通用产出下限（cap-link）**：把 v0.6 第三阶段的「产出 ≥ 上限 / τ」推广到全部宇宙，
   使每个宇宙都能"填满上限"，用 `τ` 统一 pacing。

> 结论：本 PR 只做低风险修复（消除停滞，U9 可达），不改变既有节奏结论。深层 pacing 见上述候选。
