## ADR-001：将 v0.5 与 v0.6 合并为 v0.5.0 发布

| 项目 | 内容 |
|---|---|
| 状态 | ✅ 已采纳 |
| 日期 | 2026-10-11 |
| 决策者 | 维护者 |
| 关联 | Issue #16（多宇宙）、#19（舍入纪）、#20（星场背景）、#21（素材规则 v1.2）；PR #23–#31 |

### 背景

- **v0.5（多宇宙）** 与 **v0.6（舍入纪：`ee` 记法 / 双结局 / 音频基建 / 九宇宙换皮）** 两块内容在 `dev` 上**并行开发并已全部合并**，中间**没有为 v0.5 单独打 tag 或发布**。
- 版本号已长期停留在 `v0.4.0`，而 `CHANGELOG` 的 `[Unreleased]` 已累积了两代的全部改动。
- 若此时再补发一个 `v0.5.0`、把 v0.6 内容挪到 `v0.6.0`，需要**人为拆分已混在一起的提交与 CHANGELOG**，且与已合并的 PR 历史不符——发布记录会失真。

### 决策

**将 v0.5 与 v0.6 的全部内容整合为一次发布：`v0.5.0`。**

- `CHANGELOG` 的 `[Unreleased]` 定版为 `[0.5.0]`；
- 代码 `VERSION`（`js/ui/app.js`）与 `README.md` 状态同步为 `v0.5.0`；
- 条目保留各功能的**来源标签**（多宇宙 / 舍入纪 / PR 编号），但**不再单独发布 `v0.6.0`**；「舍入纪」降为**功能弧名称**，而非版本号。

### 理由

1. **如实记录历史**：所有功能确在同一批合并进 `dev`，理应同批发布。
2. **避免版本号虚增**：为一个没有独立发布节点的中间里程碑补 tag，只增加维护负担。
3. **降低发布风险**：一次 `dev → main` + 一个 tag，GitHub Pages 只部署一次。

### 影响

- `v0.5.0` 之后的下一版本从 **`v0.6.0`** 起（若仍有排期），但它将是**全新的变更集**，不再包含本次已发布内容。
- 仍待办、归入既有「舍入纪」叙事的**素材类**事项（结局过场像素画 ×2 等）不阻塞本次发布，可在后续版本补齐。
- 流程改进：后续若再出现「两批内容并行合并」，应**在合并前**决定是否同批发布，或在 `CHANGELOG` 中预先分组。

### 被否方案

| 方案 | 否决原因 |
|---|---|
| 补发 `v0.5.0`，另发 `v0.6.0` | 需拆提交 / 拆 CHANGELOG，与已合并历史不符 |
| 直接发 `v0.6.0`（跳过 v0.5.0） | 「多宇宙」这一结构性里程碑将无版本可指；且 0.4 → 0.6 跳号易被误读为缺失 0.5 |
