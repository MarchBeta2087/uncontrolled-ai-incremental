## ADR-001：将 v0.5 与 v0.6 合并为 v0.5.0 发布

| 项目 | 内容 |
|---|---|
| 状态 | ✅ 已采纳 |
| 日期 | 2026-10-11 |
| 决策者 | 维护者 |
| 关联 | Issue #16（多宇宙）、#19（舍入纪）、#20（星场背景）、#21（素材规则 v1.2）；PR #23–#31 |

### 背景

- **v0.5（多宇宙）** 与 **v0.6（舍入纪：`ee` 记法 / 双结局 / 音频基建 / 九宇宙换皮）** 两块内容在 `dev` 上**并行开发并已全部合并**，中间**没有为 v0.5 单独打 tag 或发布**。
- 版本号已长期停留在 `v0.4.0`，而 `CHANGELOG` 的 `[Unreleased]` 已累积了两代的全部改动。
- 若此时再补发一个 `v0.5.0`、把 v0.6 内容挪到 `v0.6.0`，需要**人为拆分已混在一起的提交与 CHANGELOG**，且与已合并的 PR 历史不符——发布记录会失真。

### 决策

**将 v0.5 与 v0.6 的全部内容整合为一次发布：`v0.5.0`。**

- `CHANGELOG` 的 `[Unreleased]` 定版为 `[0.5.0]`；
- 代码 `VERSION`（`js/ui/app.js`）与 `README.md` 状态同步为 `v0.5.0`；
- 条目保留各功能的**来源标签**（多宇宙 / 舍入纪 / PR 编号），但**不再单独发布 `v0.6.0`**；「舍入纪」降为**功能弧名称**，而非版本号。

### 理由

1. **如实记录历史**：所有功能确在同一批合并进 `dev`，理应同批发布。
2. **避免版本号虚增**：为一个没有独立发布节点的中间里程碑补 tag，只增加维护负担。
3. **降低发布风险**：一次 `dev → main` + 一个 tag，GitHub Pages 只部署一次。

### 影响

- `v0.5.0` 之后的下一版本从 **`v0.6.0`** 起（若仍有排期），但它将是**全新的变更集**，不再包含本次已发布内容。
- 仍待办、归入既有「舍入纪」叙事的**素材类**事项（结局过场像素画 ×2 等）不阻塞本次发布，可在后续版本补齐。
- 流程改进：后续若再出现「两批内容并行合并」，应**在合并前**决定是否同批发布，或在 `CHANGELOG` 中预先分组。

### 被否方案

| 方案 | 否决原因 |
|---|---|
| 补发 `v0.5.0`，另发 `v0.6.0` | 需拆提交 / 拆 CHANGELOG，与已合并历史不符 |
| 直接发 `v0.6.0`（跳过 v0.5.0） | 「多宇宙」这一结构性里程碑将无版本可指；且 0.4 → 0.6 跳号易被误读为缺失 0.5 |

## ADR-002：字体许可扩展为「OFL 优先，兼容许可证亦可」，并采用 SevenFifteen 作为非 Fusion 脚本兜底字体

| 项目 | 内容 |
|---|---|
| 状态 | ✅ 已采纳 |
| 日期 | 2026-10-11 |
| 决策者 | 维护者 |
| 关联 | `docs/素材与授权规则-v1.3.md`；SevenFifteen 接入 PR |

### 背景

- 项目原将字体统一限定为 **SIL OFL 1.1**；但 §1 许可矩阵本就允许 **CC BY 4.0**（与 CC BY-SA 4.0 单向兼容）。
- 为后续多语言（阿拉伯语、印地语等）准备字体时发现：
  - **Handjet**（OFL）覆盖阿拉伯，但**不含天城文（印地语）**；
  - **SevenFifteen Mono Rounded**（CC BY 4.0，Douglas Vautour / Burpy Fresh）**同时覆盖天城文（含连字）与阿拉伯（含连写）**，还含希腊 / 西里尔 / 希伯来 / 泰文。

### 决策

1. **§4 字体规则扩展**：字体**优先 OFL**，亦接受**与 CC BY-SA 4.0 兼容、可商用、可修改**的许可证（如 CC BY 4.0），须在 `ASSETS.md` 与 `LICENSE.txt` 中署名。
2. **采用 SevenFifteen 作为非 Fusion 脚本的兜底字体**（优先级 **Fusion > SevenFifteen**），**取代 Handjet**（后者不含天城文，功能被完全覆盖）。

### 理由

- 许可上 CC BY 4.0 与项目素材许可兼容，且无 OFL 的「保留字体名」约束，使用更直接。
- 一个字体同时兜住印地语 + 阿拉伯语，减少字体数量与加载。

### 影响

- `docs/素材与授权规则` 升至 **v1.3**（全仓库链接同步）。
- 字体栈统一为 `Fusion > SevenFifteen > 通用族`；SevenFifteen 子集化为 WOFF2（3.0 MB → 107 KB），仅保留 Fusion 不覆盖的脚本。
- 后续引入印地语 / 阿拉伯语等语言时，字形即可用。

### 被否方案

| 方案 | 否决原因 |
|---|---|
| 维持 OFL-only | 印地语像素字体多为 CC BY / 自定义许可，OFL-only 会把可用字体限制死 |
| 保留 Handjet 且新增 SevenFifteen | 功能重叠（阿拉伯两边都有），Handjet 无法覆盖天城文，徒增一份字体 |

## ADR-003：v2.0 数值红线与上游大数库跟踪

| 项目 | 内容 |
|---|---|
| 状态 | ✅ 已采纳 |
| 日期 | 2026-10-12 |
| 决策者 | 维护者 |
| 关联 | Issue #50；上游 [dlsdl/metanum #17](https://github.com/dlsdl/metanum/issues/17)、[VeryrrDefine/PowiainaNum.js #19](https://github.com/VeryrrDefine/PowiainaNum.js/issues/19) |

### 背景

- **数值锚点路线已排定**：v0.6 = eee120（庞加莱时间）、v0.7 = 10↑↑1e9、v1.0 = 10↑↑↑↑1e6。
- **红线内余量充足**：v1.0 锚点仅达 FGH 的 $f_5$ 层级；当前在用 **MegotaNum.js** 上限约 $f_{\omega^2+1}$（`{10, 9e15, 1, 1, 2}`）。**任意有限箭头数任意高度都低于 $f_\omega$**，故红线内余量足以覆盖 v1.x 至 v2.0 全部版本。
- **红线之外的候选上游现状**（截至 2026-10-12）：

| 库 | 上限（FGH） | 许可证 | 状态 |
|---|---|---|---|
| MegotaNum.js | ≈ $f_{\omega^2+1}$ | MIT | 在用；已 patch 其 `toJSON` 丢分量 bug |
| metanum | $f_{\varepsilon_0}$ | MIT | #17 未修（开放、零回复、多为格式/解析/序数引擎缺陷） |
| PowiainaNum.js | $f_{\omega^3+1}$ | **无** | 无法合规使用；#19 请求添加许可证 |

### 决策

1. **v2.0 之前，游戏内一切数值不得超过 MegotaNum 上限（≈ $f_{\omega^2+1}$）。**
2. **v2.0 达成后，禁止添加任何新内容，只允许修复 Bug**，直至下列条件**任意一项**满足为止：
   - **条件 1**：metanum 的已知 Bug 被修复——操作定义：**#17 被关闭且修复随发布版可用**（不接受「主分支已修但未发版」）；
   - **条件 2**：PowiainaNum.js 可被合规使用——操作定义：**仓库内出现 OSI 批准的许可证文本文件**；
   - **条件 3**：出现强于或相当于 PowiainaNum.js（$f_{\omega^3+1}$）、兼容 GPL-3.0-or-later、无严重 Bug 的大数库——**「有人」包括本项目自己**。
3. 条件满足后，**通过 Num 适配器（`js/core/num.js`）换库，只动一个文件**；smoke 回归与 balance-sim 为现成验收工具。
4. **路线（条件 3 的主动分支）**：先修 metanum，修不动则自造 **HeptoNum.js**（目标上限 $f_{\omega^4+1}$、MIT；命名取自 heptation，维持原名不译，README 必须明确标注 FGH 层级）。

### metanum #17 修复成本评估（2026-10-12）

评估方式：clone `dlsdl/metanum` @ `main`（v2.0.2，`metanum.js` 6,888 行 + `format-metanum.js` 2,101 行），Node 22 逐条复现。

| # | 缺陷 | 复现（实测） | 根因定位 | 修复成本 |
|---|---|---|---|---|
| 1 | BEAF/LAN 越 MSI | `BEAF(10,16)` 值正确（`E16`），但 `toBeaf()` 输出 `{16}`，roundtrip 失真 | `P.toBeaf` 对 layer0 / E 级直接用指数当值，丢底数 | 低（格式层 ~10 行；**值本身未错**） |
| 2 | toBeaf 大 LAN | `fromString("G600").toBeaf()` → `{10000000000}`、`E100#2` → `{0}`，丢层 | 同上 | 中（需忠实重建 BEAF 行，含 `?` 占位先例） |
| 3 | `pow(10, α)`，α ≤ -324 | `MetaNum.pow(10,-324)` → 正 `E324`（`sign=+1`）；而 `fromString("1E-324")` 正确 | `P.pow` 的 `x.eq(TEN) && !isSmall(other)` 快路径未排除负指数 | **低（1~2 行）** |
| 4 | Z 记法重复 | `format(fromString("ZZ152416"))` → `1.000Z3`（issue 所述「Z3」），且 roundtrip `eq=false` | `format-metanum.js` 的 `metaPolarize` repeat 计数 / `letterTokenOf` | 中（纯格式层，多 Z / 多字母边界多） |
| 5 | `!Aa` 小数 / 混合 | `fromString("!Aa1.5")`→0、`fromString("!2Aa3")`→0、`format(fromString("!Aa10"))`→`!1.000N10` | `Q.fromString` 的 `!` 分支 + 格式发射两处 | 中高（解析 + 格式） |
| 6 | `2{ω^…}2 ≠ 4` | 序数对角化（`2{ω^ω2}2` 等）不等 4 | `_ordinalHyperop` / `_beafOrdinal` 核心序数算术 | **高**（回归面覆盖整个 $f_{\varepsilon_0}$ 引擎） |

**额外风险**：仓库无 CI，`npm test` 指向不存在的 `test.js`；上游最近提交 2026-10-05、9 star、#17 零回复——修复意愿与节奏不可控。

### 结论

- **低垂果实（缺陷 3，可能含 1）**：改动小，可作为向 #17 提交的 PR 素材；但**必须上游接纳并发布**才满足条件 1。
- **中等（缺陷 2 / 4 / 5）**：属格式 / 解析层，可在 fork 内修，但仍受「必须发布」约束。
- **核心（缺陷 6 + 序数引擎）**：BEAF/LAN 在 MSI 以上断裂是设计级问题，回归面覆盖整个 $f_{\varepsilon_0}$ 引擎，修复不可控。
- 因此：**不把条件 1 作为 v2.0 的关键路径**；按路线准备分支 B（HeptoNum.js），在 v2.0 到来前启动「记号规范先行」。**当前无紧急动作**——v2.0 前所有数值仍在红线内。

### 理由

- 红线本质是**内容纪律约束**（v2.0 前不设计对角化之后的机制），不是容量约束：$f_5$ → $f_{\omega^2+1}$ 的余量足够装下 v1.x~v2.0 全部版本。
- 提前换库会把「数值容量」与「机制设计」耦合，反而诱导越线发明；先冻结口径、按版本观测，成本最低。

### 影响

- Num 适配器的「换库只改一个文件」约定是本红线的工程前提，**已具备**。
- 每版本评审时例行扫一眼三条件状态（maintainer 例行）。
- TODO.md 远期区新增「v2.0 红线与三条件跟踪」，挂上游 Issue 链接。

### 被否方案

| 方案 | 否决原因 |
|---|---|
| 现在直接切 metanum 享受 $f_{\varepsilon_0}$ | #17 核心缺陷未修，BEAF / Z / `!Aa` 不可靠；且 v2.0 前红线本就禁止 |
| 直接切 PowiainaNum.js | 无许可证，无法合规使用 |
| 等 MegotaNum 上游扩容 | 上游能力已定档 $f_{\omega^2+1}$，无扩容计划 |
| 立即自造 HeptoNum.js | 当前无内容需求（红线内余量充足），过早投入 |
